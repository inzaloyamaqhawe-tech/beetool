# Backend integration guide

This app currently runs entirely in the browser — every read and write goes
through `js/api.js`, which today is backed by `localStorage` (see
`js/data.js`). **`js/api.js` is the only file that needs to change** to wire
up a real backend; nothing in `js/app.js` talks to storage directly.

**A real implementation of everything below already exists** in
`backend/` — plain PHP + MySQL, built for Xneelo shared hosting (see
`backend/README.md` for deploy steps). This document is still the
authoritative contract; `backend/` is that contract implemented, kept
deliberately in sync with it (same table names, same column names, same
endpoint shapes) — if you're building your own backend instead, treat this
file as the spec and `backend/` as a fully worked example of following it.

Read this alongside `js/api.js` — every function there has a matching doc
comment with the same contract described here, and is the authoritative
source if this document and the code ever disagree.

## How to activate a real backend

1. Build the database tables and endpoints below.
2. In `js/api.js`, set `API_BASE_URL` to the deployed API's base URL.
3. Flip `USE_REMOTE_API` to `true`.
4. Each `Api.*` function already has a working `fetch()` implementation
   behind an `if (USE_REMOTE_API)` branch — there is no rewrite to do, just
   endpoints to stand up that match the shapes below.
5. Wire real authentication and call `Api.setAuthToken(token)` with the
   result — every remote call already attaches it as
   `Authorization: Bearer <token>`.

## Database schema — tables to create

Everything the frontend needs comes from **one resource: a Scorecard.**
There is no separate "add a person" endpoint — the workforce roster (what
the frontend calls "Add Person" on Management Control), the ownership
shareholder register, the ESD supplier register, and the SED beneficiary
list are all just child tables of `scorecards`, saved together whenever the
Save button is clicked. That single save (`PUT /api/scorecards/:id`)
receives the whole nested object shown below and should upsert every child
table in one transaction.

Two ways to store the nested per-element data — pick whichever suits your
stack; both satisfy the same request/response contract in `js/api.js`:

- **Option A — normalized tables** (below). Better if you ever want to query
  across scorecards (e.g. "every supplier with an expired certificate this
  quarter"). This is the recommended default.
- **Option B — one JSONB/JSON column**. Add a single `data` (JSON) column to
  `scorecards` holding everything from `general` downward, keyed exactly as
  `js/data.js`'s `blankScorecard()` produces it. Fastest to build, harder to
  query. Reasonable if reporting needs stay simple.

The column names below are the suggested snake_case DB names; the bracketed
name is the exact field in the JS object each one maps to, so nothing gets
lost in translation either way.

### `accounts`
*This is real, not speculative: Centenary Networks manages B-BBEE scorecards
for more than one entity under its umbrella (sponsors/partners/companies it
supports). The Accounts page (`#/accounts`) lists every account, lets you
add a new one, and switches between them — each account genuinely sees only
its own scorecards, company profile and B-BBEE performance.*

*Locally (no backend yet) this is implemented as real per-account isolation,
not a cosmetic label: every account gets its own `localStorage` blob keyed
`centenaryBee.v1.<accountId>` (see `storageKeyFor()`/`loadState()`/
`saveState()` in `js/data.js`), while a small shared index
(`centenaryBee.accounts`) tracks the account roster, which one is active,
and the signed-in session. `addAccount(name)` creates a fresh, genuinely
empty blob for the new account (no Centenary sample data carried over);
`switchAccount(id)` flips the active pointer and reloads the page so every
part of the app — STATE, the nav, every cached reference — picks up the new
account's data with nothing stale left over. What a real backend adds on
top: cross-device sync (today each browser/device has its own local
accounts), and actual authorization (anyone with the browser can currently
add/switch accounts and see every account's summary on the Accounts page —
there's no login gating who can see which account yet, since there's no
real auth; see "Team"/sessions below).*

| Column | Type | JS field |
|---|---|---|
| id | uuid / int, PK | `accounts[].id` (locally: `acc_<random>`, generated by `uid('acc')`) |
| name | text | `accounts[].name` |
| tagline | text | `company.tagline` (each account has its own — not shared with `accounts.name`) |
| logo_asset_path | text | `company.logoAssetPath` — a URL once uploads exist |
| created_at | timestamptz | `accounts[].createdAt` |

`scorecards.account_id` (see below) scopes every scorecard to one account —
list/get/create/update endpoints all need to filter/authorize by the
signed-in user's account membership once real auth exists. Migrating this
to a real backend: `GET /api/accounts` returns the row set that's currently
`getAccountsIndex().accounts`; each account's nested data (scorecards,
implementation, scenarios) is exactly the same shape already documented
below, just scoped server-side by `account_id` instead of by
`localStorage` key.

> each signed-in user's own `user_accounts.role` row instead of one shared

> instead of `session.role` once `Api.setAuthToken()` is wired up.

| leviable_amount | numeric | `general.leviableAmount` |
| industry | text | `general.industry` |
| targets | jsonb | `targets` (see note below) |
| goals | jsonb | `goals` (see note below) |

| updated_at | timestamptz | server-managed |

> **Why `targets`/`goals` stay as JSON even in the "normalized" option:**
> they're ~25 numeric scoring-target coefficients (e.g. "black ownership
> target %") that are never queried independently — they're only ever read
> or written as a whole alongside their scorecard. Normalizing every one
> into its own column adds a lot of schema for no query benefit. If you
> later do want to query/report on individual targets, split this out into
> a `scorecard_targets` key/value table (`scorecard_id, path, value`).
>
> **`targets` also carries the EAP Demographic Matrix's target grid**
> (`targets.eap` — a race x gender percentage grid, `blankEapTargets()` in
> `js/data.js`) — it's just another key inside this same JSON blob, so EE
> Insights' EAP matrix needed no schema change of its own; only the fields
> below (Payment Schedules, Ownership Transaction Schedule, Supplier
> Qualification, and extending evidence status to shareholders/programmes)
> needed real columns, since those involve either child rows or fields other
> tabs/`calc.js` read directly rather than round-tripping opaquely.
>
> **`comparison_scorecard_id`** backs Scorecard Insights' Period Comparison
> card (`periodComparisonCard()` in `js/app.js`) — which other scorecard
> this one is currently being compared against. It's a UI preference, not
> scoring data, and self-references this same table; `ON DELETE SET NULL` so
> deleting the comparison target doesn't take this scorecard down with it.

## Endpoints

All request/response bodies are JSON unless noted. All list endpoints
return full objects (this is a small internal tool, not a paginated public
API) — add pagination later only if it becomes a real problem.

### Auth (not yet implemented client-side — see "Auth" below)

| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/auth/login` | `{ email, password }` | `{ token, user }` |
| POST | `/api/auth/logout` | — | `204` |
| GET | `/api/auth/me` | — | `user` |

### Accounts

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/accounts` | — | `Account[]` — every account the signed-in user belongs to; the top bar's Accounts menu lists these |
| PATCH | `/api/session/account` | `{ accountId }` | `200` — switches which account subsequent `/api/scorecards` calls are scoped to |

### Scorecards

*Scoped to the current account (see Accounts above) — a `GET /api/scorecards`
without a real backend today just returns `STATE.scorecards`, which is the
single account's data since there's only one account locally. The real
implementation in `backend/api/scorecards.php` requires an explicit
`?account_id=...` query param on the list GET (and `account_id` in the POST
body) rather than an invisible "current account" kept server-side — see
that file's top comment for why.*

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/scorecards?account_id=...` | — | `Scorecard[]` |
| GET | `/api/scorecards/:id` | — | `Scorecard` \| `404` |
| POST | `/api/scorecards` | `Partial<Scorecard>` (usually just `{ size, description }`) | `201` `Scorecard` (server fills in every other field via the same defaults as `blankScorecard()`) |
| PUT | `/api/scorecards/:id` | full `Scorecard`, i.e. every table above assembled back into the nested shape | `200` `Scorecard` |
| DELETE | `/api/scorecards/:id` | — | `204` |

There is **no separate archive endpoint** — archiving is a normal `PUT` with
`archived: true`. There is likewise **no separate "add person" endpoint** —
adding a row to `people`/`shareholders`/`suppliers`/`sed_beneficiaries`
happens client-side and is committed on the next `PUT` of the whole
scorecard (see "Local-draft vs. explicit save" below).

### Portfolio of Evidence uploads

The one exception to "everything rides along with the scorecard PUT" — a
file can't travel inside a JSON body, so it gets its own endpoint. This is
the User Portfolios screen: one consolidated PDF per person, replacing
several separate individual document submissions.

| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/scorecards/:id/people/:personId/portfolio` | `multipart/form-data`, field `file` (PDF only) | `201` `{ status: 'Uploaded (Pending Review)', fileUrl, uploadedAt }` |
| PATCH | `/api/scorecards/:id/people/:personId/portfolio` | `{ status: 'Approved'\|'Rejected', rejectionNote? }` | `200` updated portfolio fields |
| GET | `/api/scorecards/:id/portfolios` | — | `PersonPortfolio[]` (list, for a future reviewer/verification-agency view) |

Enforce **both** the PDF-only type and a max file size (this tool warns at
15MB client-side — `PORTFOLIO_MAX_FILE_MB` in `js/data.js` — confirm and
enforce your own real limit server-side; never trust the client check
alone). Recommend object storage (S3-compatible) for the file bytes, with
the database only storing the returned URL. `PATCH` is a reviewer-side
action — there's no reviewer-facing UI or login in this tool yet, so nothing
calls it remotely today (the local demo simulates it by letting you toggle
status directly); it exists here for whenever a verification-agency view or
admin tool consumes it.

## Error format

Any non-2xx response should return:

```json
{ "error": { "message": "human-readable string", "code": "MACHINE_CODE" } }
```

`js/api.js`'s `apiFetch()` helper already reads `error.message` out of a
failed response and throws it — no frontend change needed as long as errors
look like this.

## Auth

There is no login screen yet — this tool is currently used without
per-person sign-in. When real auth exists:

1. Add a login screen that calls `POST /api/auth/login` and stores the
   returned token via `Api.setAuthToken(token)`.
2. Every other `Api.*` call already sends `Authorization: Bearer <token>`
   automatically (see `authHeaders()` in `js/api.js`) — nothing else to
   change on the frontend.

## What's intentionally client-side only (no backend needed)

- **CSV / Excel / PDF exports** — all generated entirely in the browser
  (`js/app.js`: `exportScorecardCSV`, `exportScorecardExcel`,
  `exportScorecardPDF`, `exportPersonPDF`). Excel uses the "HTML table saved
  as `.xls`" trick (no library available offline); PDF uses the browser's
  native print dialog. These do not need server endpoints. Note
  `exportPersonPDF` (Management Control roster's "PDF" button, a one-page
  auto-generated demographic summary) is **not** the same thing as the User
  Portfolios upload — that one's a real scanned document bundle the person
  supplies, this one's a system-generated cover sheet; they're complementary.
- **User Portfolios' local file storage** — until the upload endpoint above
  exists, attached PDFs are cached in the browser's IndexedDB
  (`js/portfolio-store.js`), on this device only. Nothing to build for this;
  it's superseded once `POST .../portfolio` is live (see `USE_REMOTE_API` in
  `js/api.js`).
- **Per-dataset CSV import/export** (under Management Control, Ownership,
  Enterprise & Supplier Development, Socioeconomic Development and
  Implementation Plan) — a bulk add/pull mechanism for each roster/register,
  entirely client-side (`exportSectionCSV`/`importSectionCSV` in `js/app.js`).
- **All the B-BBEE scoring math** (`js/calc.js`) — pure functions over
  whatever Scorecard object they're given. The backend should treat a
  Scorecard as opaque data to store; it does not need to reimplement the
  scoring logic unless you want server-side validation of submitted scores.
- **Scorecard Insights' Cost Per Point Analysis, EAP's for this period, and
  Peer Pay Check** (Management Control) — all derived at render time from
  fields already listed above (`costPerPointCard`, `eapCard`,
  `calcPayFairness` in `js/app.js`/`js/calc.js`). Nothing new to store; the
  backend only needs the underlying spend/roster fields it already has.

## Local-draft vs. explicit save (important for expectations)

Editing a field (a text box, a percentage, a checkbox — including adding a
row to any roster) writes immediately to local state so it feels instant —
it does **not** call `Api.*` on every keystroke. The explicit **Save**
button on every scorecard screen is what calls `Api.saveScorecard()`. This
is deliberate: a real network call on every keystroke would be slow and
wasteful. If you want autosave-to-server later, the natural place is a
debounced call to the same `Api.saveScorecard()` function — the local-write
path does not need to change.
